# Search Criteria & Source Capabilities

## 1. Purpose

This document defines the generic search model of the AI Job Search Agent and its adaptation to the three sources selected for the hackathon prototype:

- Himalayas
- RemoteOK
- Lever

The objective is to separate:

1. the user's search intent;
2. the generic `SearchCriteria` understood by the agent;
3. the capabilities actually supported by each source;
4. the source-specific query generated by each connector.

The model is source-independent. The current source mappings are an implementation of this model for the prototype and can be extended later.

---

## 2. Core principle

A user's preferences must not be sent identically to every source.

Each source exposes different search parameters, filters, accepted values, data structures, pagination mechanisms, and access constraints.

Therefore:

```text
UserProfile
    ↓
SearchPreferences
    ↓
SearchCriteria
    ↓
SourceCapabilities
    ↓
Source-specific Query
    ↓
Connector
    ↓
Raw Offers
```

`SearchCriteria` is the generic internal contract. `SourceCapabilities` determines which parts of that contract can actually be used when querying a given source.

---

## 3. SearchPreferences vs SearchCriteria

### SearchPreferences

Represents what the user currently wants to find.

```json
{
  "keywords": ["React", "Next.js"],
  "locations": ["Dakar", "Senegal"],
  "remote": true,
  "seniority": "mid",
  "employmentType": "full-time"
}
```

### SearchCriteria

The normalized, executable representation of those preferences. It is not tied to a particular platform.

```text
SearchPreferences
        ↓
SearchCriteria
```

The agent adapts the criteria according to each source's capabilities.

---

## 4. Generic SearchCriteria

The prototype uses the following conceptual criteria:

| Criterion | Meaning | Potential role |
|---|---|---|
| `keywords` | Terms related to the desired job | Search + Matching |
| `jobTitles` | Desired job titles | Search + Matching |
| `locations` | Desired geographic locations | Search + Matching |
| `countries` | Desired countries | Search + Matching |
| `remote` | Remote-work preference | Search + Matching |
| `seniority` | Desired experience/seniority | Search + Matching |
| `employmentType` | Full-time, part-time, contract, etc. | Search + Matching |
| `skills` | Technical/professional skills | Search + Matching |
| `salary` | Desired compensation range | Search + Matching |
| `companies` | Target companies | Search + Matching |
| `timezone` | Desired timezone compatibility | Search + Matching |
| `department` | Desired department | Search |
| `team` | Desired team | Search |
| `tags` | Source/platform-specific tags | Search + Matching |

Not every criterion is supported by every source.

---

## 5. Three levels of criteria

### Source-searchable

The source explicitly supports the criterion as an input to its search/query mechanism.

### Source-returned but not necessarily searchable

The source returns the information in an offer, but current evidence does not establish that it can be used as an input filter.

The agent must not assume that an output field is also an input parameter.

### Matching-only

The information is used after retrieval to evaluate compatibility. For example, skills extracted from a description may be used by matching even if the source does not expose an equivalent search parameter.

---

## 6. Source Capabilities

`SourceCapabilities` describes what a connector can actually do with the generic criteria.

```text
SourceCapabilities
├── search
├── filters
├── pagination
├── format
├── authentication
└── constraints
```

This layer prevents the agent from sending unsupported parameters to a source.

# 7. Himalayas

## Why it is important

Himalayas is the main demonstration source for structured search.

Our test identified REST/JSON, no API key observed, a maximum of 20 offers per request in the tested response, cursor pagination, structured employment type, seniority, location restrictions, timezone restrictions, categories, salary, publication and expiry dates.

The response contains:

```text
updatedAt
offset
limit
totalCount
jobs[]
```

Job fields include:

```text
title
companyName
employmentType
minSalary
maxSalary
salaryPeriod
seniority[]
currency
locationRestrictions[]
timezoneRestrictions[]
categories[]
parentCategories[]
description
pubDate
expiryDate
applicationLink
guid
```

## Capability mapping

| SearchCriteria | Himalayas |
|---|---|
| `keywords` | Supported / exact parameter semantics to verify before implementation |
| `jobTitles` | Potentially through keyword search; dedicated parameter not established |
| `locations` | Supported through location-related search/filter capabilities |
| `countries` | Supported |
| `remote` | Supported through remote/worldwide-related parameters |
| `seniority` | Supported |
| `employmentType` | Supported |
| `skills` | Dedicated search parameter not established |
| `salary` | Returned as structured data; search capability requires verification |
| `companies` | Search capability available |
| `timezone` | Supported |
| `department` | Not established |
| `team` | Not established |
| `tags` | Not established as the primary search mechanism |

## Role in the prototype

```text
SearchCriteria
      ↓
Structured source query
      ↓
JSON
      ↓
Normalization
```

# 8. RemoteOK

## Why it is important

RemoteOK demonstrates heterogeneous source formats and a relatively simple offer structure.

Our tested JSON response exposed:

```text
id
slug
date
epoch
company
company_logo
position
tags
description
location
apply_url
salary_min
salary_max
url
```

The source also exposes an RSS feed.

This allows:

```text
RemoteOK JSON ──→ JSON Parser ──┐
                                ├──→ JobOffer
RemoteOK RSS  ──→ RSS Parser ───┘
```

## Capability mapping

| SearchCriteria | RemoteOK |
|---|---|
| `keywords` | Dedicated API search parameter not established |
| `jobTitles` | Dedicated API search parameter not established |
| `locations` | Returned in offers; search capability not established |
| `countries` | Dedicated API filter not established |
| `remote` | Intrinsic to the source's remote-job scope |
| `seniority` | Dedicated search parameter not established |
| `employmentType` | Not established |
| `skills` | Potentially available through `tags` / description; exact search semantics require verification |
| `salary` | Returned as `salary_min` / `salary_max`; search filtering not established |
| `companies` | Returned; search capability not established |
| `timezone` | Not established |
| `department` | Not established |
| `team` | Not established |
| `tags` | Returned as structured tags |

## Role in the prototype

RemoteOK demonstrates:

1. source-specific parsing;
2. JSON normalization;
3. RSS/XML normalization;
4. structured tags;
5. different source schemas converging on the same `JobOffer`.

The prototype must not infer search parameters merely because a field exists in the response.

# 9. Lever

## Why it is important

Lever demonstrates a fundamentally different source-access model.

The Postings API uses:

```text
GET /v0/postings/{SITE}?mode=json
```

`SITE` identifies the company's Lever job board.

Therefore Lever is not treated as a global job-search engine in the prototype. It demonstrates that the agent understands source-specific capabilities and prerequisites.

## Capability mapping

| SearchCriteria | Lever |
|---|---|
| `keywords` | Not established as global full-text search |
| `jobTitles` | Returned in posting data; global search not established |
| `locations` | Supported in posting/job-board data |
| `countries` | Dedicated query parameter not established |
| `remote` | Depends on returned posting/location information |
| `seniority` | Dedicated query parameter not established |
| `employmentType` | Mapped to `categories.commitment` |
| `skills` | Dedicated query parameter not established |
| `salary` | Not established in the tested core structure |
| `companies` | Implicitly required through the job-board `SITE` |
| `timezone` | Not established |
| `department` | Supported |
| `team` | Supported |
| `tags` | Not established |

Tested/documented fields include:

```text
id
text
categories.location
categories.commitment
categories.team
categories.department
categories.allLocations
```

Pagination is available through `skip` and `limit`.

## Role in the prototype

```text
Generic SearchCriteria
        ↓
SourceCapabilities
        ↓
"Lever requires a SITE"
        ↓
Lever-specific query
        ↓
Job postings
```

The point is not to pretend that Lever has the same search capabilities as Himalayas. The point is to show that the architecture adapts to the source.

# 11. Query Translation

The agent should never send every `SearchCriteria` field to every API.

Instead:

```text
SearchCriteria
      ↓
SourceCapabilities
      ↓
QueryBuilder
      ↓
Source-specific query
```

Conceptual interfaces:

```text
buildQuery(
    criteria: SearchCriteria,
    capabilities: SourceCapabilities
): SourceQuery
```

Examples:

```text
HimalayasQueryBuilder
RemoteOKQueryBuilder
LeverQueryBuilder
```

Each builder translates only supported criteria.

---

# 12. Unsupported Criteria

An unsupported criterion must never be silently treated as supported.

Possible states:

```text
SUPPORTED
NOT_SUPPORTED
NOT_VERIFIED
MATCHING_ONLY
REQUIRES_SOURCE_CONTEXT
```

Example:

```text
User:
seniority = "mid"

RemoteOK:
seniority search = NOT_VERIFIED

Action:
do not send a fabricated seniority parameter.
```

For Lever:

```text
User:
React + Dakar

Lever:
global search = NOT_SUPPORTED

Action:
Lever cannot be queried globally from this criterion alone.
A SITE/job board context is required.
```

---

# 13. Search vs Matching

The prototype must maintain a strict distinction:

```text
                 SEARCH
                   │
                   ▼
        "Can this source find it?"
                   │
                   ▼
               JobOffer
                   │
                   ▼
                MATCHING
                   │
                   ▼
       "Does it fit the user?"
```

A criterion may therefore be searchable, returned-only, or matching-only.

---

# 14. Relation to UserProfile

The final flow is:

```text
UserProfile
      ↓
SearchPreferences
      ↓
SearchCriteria
      ↓
SourceCapabilities
      ↓
Source-specific queries
      ↓
Sources
      ↓
Raw Offers
      ↓
Normalization
      ↓
JobOffer
      ↓
UserProfile + SearchPreferences
      ↓
Matching
```

`UserProfile` remains the source of truth for the user's complete professional profile.

`SearchCriteria` is the executable projection of the current search intent.

# 15. Prototype Objective

The hackathon prototype should demonstrate:

```text
1. User defines a search intention
        ↓
2. Agent creates SearchCriteria
        ↓
3. Agent inspects source capabilities
        ↓
4. Agent creates source-specific queries
        ↓
5. Connectors retrieve offers
        ↓
6. Different formats are parsed
        ↓
7. All offers become JobOffer
        ↓
8. Offers are deduplicated
        ↓
9. Matching evaluates compatibility
        ↓
10. Agent explains the results
```

The central demonstration is:

> We built an agent that adapts one generic search intention to heterogeneous job sources and brings their results into a common model.

---

# 16. Verification and scope

This is an architectural specification for the prototype.

Where a source capability has not been explicitly verified, it is marked `Not established`, `Not verified`, or requires confirmation.

The following must not be inferred automatically:

- an output field is a valid input parameter;
- an `applyUrl` authorizes automated applications;
- technical access constitutes contractual authorization;
- a public endpoint permits unrestricted aggregation or redistribution.

These questions remain governed by `connectors.md` and `research-protocol.md`.
