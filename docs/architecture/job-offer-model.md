# JobOffer — Canonical Domain Model

**Status:** MVP / Proof of Concept — validated model  
**Purpose:** Canonical representation of job offers aggregated from heterogeneous sources.

## 1. Purpose

`JobOffer` is the canonical domain model used by the AI Job Search Agent after ingestion and normalization.

It is intentionally richer than the intersection of fields exposed by individual job sources. Each source populates the fields it can reliably provide; unavailable information remains unknown/null.

`JobOffer` is a domain model, not a copy of any source API.

The model supports:

- multi-source aggregation;
- semantic normalization;
- complete offer presentation;
- filtering;
- matching against a user profile;
- explanation;
- deduplication;
- provenance and traceability;
- future monitoring and lifecycle management.

## 2. Pipeline Position

```text
Source
  ↓
Connector
  ↓
RawOffer
  ↓
Parsing
  ↓
Normalization
  ↓
JobOffer
  ↓
Deduplication
  ↓

  ↓

  ↓

```

`RawOffer` preserves what the source actually returned. `JobOffer` represents our normalized interpretation.

## 4. Identity

### `identity.id`
Internal identifier generated by the application. It is independent from the identifier used by the source.

### `identity.sourceId`
Identifier of the offer in the originating source.

Examples:

```text
RemoteOK → id
Himalayas → guid
Lever → id
```

### `identity.slug`
Source slug when available.

### `identity.offerUrl`
URL of the specific offer page on the source.

## 5. Source and Provenance

```text
source
├── name
├── url
└── retrievedAt
```

- `name`: normalized source name, e.g. Himalayas, RemoteOK, Lever.
- `url`: base URL of the originating platform/source.
- `retrievedAt`: timestamp at which the connector retrieved the offer.

URL semantics are deliberately distinct:

```text
source.url
    → source/platform

identity.offerUrl
    → specific offer page

application.applyUrl
    → candidate application destination
```

## 6. Position

```text
position
├── title
├── sourceSummary
├── summary
├── description
├── responsibilities[]
├── requirements[]
├── qualifications[]
├── skills[]
├── benefits[]
└── categories[]
```

- `title`: normalized job title.
- `sourceSummary`: summary/excerpt explicitly provided by the source.
- `summary`: system-generated synthesis for fast user comprehension.
- `description`: full normalized description.
- `responsibilities[]`: normalized responsibilities explicitly supported by the offer.
- `requirements[]`: normalized job requirements.
- `qualifications[]`: degrees, certifications, or other qualifications explicitly stated by the source.
- `skills[]`: technical or professional skills.
- `benefits[]`: benefits explicitly stated by the source.
- `categories[]`: normalized categories or tags.

Generated `summary` is derived data and is not authoritative. It must never invent requirements, experience, salary, technologies, or benefits.

## 7. Company

```text
company
├── name
├── id
├── slug
├── description
├── logoUrl
├── websiteUrl
└── location
```

All company properties are optional except where the source reliably provides them. The system must not invent company information.

## 8. Location

```text
location
├── locations[]
├── cities[]
├── countries[]
├── remote
├── remoteScope
├── locationRestrictions[]
└── timezoneRestrictions[]
```

The model intentionally goes beyond a simple location string.

`remoteScope` may use values such as:

```text
GLOBAL
REGION
COUNTRY
TIMEZONE
HYBRID
UNKNOWN
```

Only assign a specific scope when the source supports it.

`remote = true` does not imply that the offer is accessible from every country.

## 9. Employment

```text
employment
├── type
├── seniority
├── department
├── team
└── schedule
```

Initial canonical values for `type`:

```text
FULL_TIME
PART_TIME
CONTRACT
FREELANCE
INTERNSHIP
TEMPORARY
OTHER
UNKNOWN
```

Initial canonical values for `seniority`:

```text
INTERN
ENTRY_LEVEL
JUNIOR
MID
SENIOR
LEAD
MANAGER
DIRECTOR
EXECUTIVE
UNKNOWN
```

`seniority` is not equivalent to years of experience. The system must not infer a precise number of years solely from a seniority label.

## 10. Experience

```text
experience
├── minimumYears
└── maximumYears
```

Example: `3+ years` becomes `minimumYears = 3`, `maximumYears = null`.

The system should preserve uncertainty rather than invent an upper bound.

## 11. Compensation

```text
compensation
└── components[]
    ├── type
    ├── amount
    ├── min
    ├── max
    ├── currency
    └── period
```

`components[]` allows salary + bonus + equity or other combinations.

Initial canonical `type` values:

```text
SALARY
HOURLY_RATE
DAILY_RATE
COMMISSION
BONUS
EQUITY
OTHER
UNKNOWN
```

Amount representation:

- `amount` → exact amount;
- `min` + `max` → range;
- `min` only → lower bound / “from”;
- `max` only → upper bound / “up to”.

The original source currency should be preserved. Currency conversion is a derived operation and must not overwrite source compensation.

A source value of `0` must not automatically be interpreted as a real zero salary without sufficient evidence.

## 12. Languages

```text
languages
├── required[]
└── preferred[]
```

Populate only when explicitly supported by the source or reliably normalized from source content.

## 13. Dates

```text
dates
├── publishedAt
├── updatedAt
├── applicationDeadline
└── expiresAt
```

- `publishedAt`: source publication date.
- `updatedAt`: last known source-side modification date.
- `applicationDeadline`: candidate-facing application deadline explicitly specified.
- `expiresAt`: offer lifecycle expiration date explicitly provided or reliably defined by the source.

```text
applicationDeadline ≠ expiresAt
```

Never infer one from the other without explicit semantic support.

## 14. Application

```text
application
├── applyUrl
├── applicationMethod
└── instructions
```

Initial `applicationMethod` values:

```text
EXTERNAL_URL
EMAIL
FORM
UNKNOWN
```

The existence of `applyUrl` does not authorize automated application. Application automation remains subject to source-specific authorization, technical constraints, and human-in-the-loop rules.

## 15. Lifecycle

```text
lifecycle
├── status
├── firstSeenAt
└── lastSeenAt
```

Initial `status` values:

```text
ACTIVE
CLOSED
EXPIRED
UNKNOWN
```

`firstSeenAt` and `lastSeenAt` are agent-side observations and must not be confused with source publication or expiration dates.

## 16. RawOffer and Canonical JobOffer

Raw source data should be kept outside the canonical model:

```text
Source
  ↓
RawOffer
  ↓
Normalization
  ↓
JobOffer
```

`RawOffer` contains the data actually returned by the source connector. `JobOffer` contains the normalized domain representation.

This separation supports debugging, investigation of normalization errors, connector improvement, provenance, and re-running normalization without necessarily calling the source again.

`raw` is therefore not a compensation-specific property in the canonical model.

## 17. Semantic Normalization

Normalization must be semantic, not simple field renaming.

### Field mapping

```text
RemoteOK.position
Himalayas.title
Lever.text
        ↓
JobOffer.position.title
```

### Value normalization

```text
"Full-time"
"Full time"
"FULL_TIME"
        ↓
FULL_TIME
```

### Semantic distinction

Fields must not be merged merely because their names look similar. For example, `closingDate` and `expiryDate` must only map to the same canonical field when source documentation establishes the same meaning.

## 18. Missing and Unknown Values

The absence of source data must not be converted into invented information.

Use `null`, `[]`, or `UNKNOWN` according to field semantics.

Examples:

```text
salary unavailable
→ compensation may be null

maximum experience not specified
→ maximumYears = null

remote scope unclear
→ remoteScope = UNKNOWN
```

## 19. Source-Specific Mapping

### Himalayas

Known fields can map conceptually as follows:

```text
title → position.title
excerpt → position.sourceSummary
description → position.description
companyName → company.name
employmentType → employment.type
seniority[] → employment.seniority
locationRestrictions[] → location.locationRestrictions
timezoneRestrictions[] → location.timezoneRestrictions
minSalary / maxSalary → compensation.components[]
currency → compensation.components[].currency
salaryPeriod → compensation.components[].period
pubDate → dates.publishedAt
expiryDate → dates.expiresAt
applicationLink → application.applyUrl
guid → identity.sourceId
```

Only implement mappings where source evidence supports the meaning.

### RemoteOK

Known fields can map conceptually as follows:

```text
id → identity.sourceId
slug → identity.slug
url → identity.offerUrl
company → company.name
company_logo / logo → company.logoUrl
position → position.title
tags[] → position.skills[] and/or categories[]
description → position.description
location → location fields according to actual value
apply_url → application.applyUrl
salary_min / salary_max → compensation.components[]
date → dates.publishedAt
```

RemoteOK data may contain incomplete or malformed offers, so normalization must tolerate missing fields.

### Lever

Lever is not a global search engine in this architecture. Its connector requires a company/job-board `SITE`.

Known fields include:

```text
id → identity.sourceId
text → position/title content according to endpoint representation
categories.location → location
categories.commitment → employment.type
categories.team → employment.team
categories.department → employment.department
categories.allLocations → location.locations[]
```

The `SITE` requirement is a source capability/context requirement, not an attribute of the canonical offer.

## 20. Deduplication Strategy

Deduplication is a processing step, not a `JobOffer` property.

```text
Raw Offers
   ↓
Parsing
   ↓
Normalization
   ↓
JobOffer
   ↓
Deduplication
   ↓
Unique JobOffer set
```

### Level 1 — Exact source identity

Use:

```text
source.name + identity.sourceId
```

### Level 2 — Offer URL

Use `identity.offerUrl` when available.

### Level 3 — Normalized field comparison

Potentially compare combinations such as:

```text
company + title + location + description
```

to detect possible cross-source duplicates.

### Future level — Semantic similarity

Semantic similarity may later be introduced for difficult cross-source cases.

For the MVP, exact source identity, URL matching, and conservative normalized-field comparison are sufficient.

Detecting a duplicate does not necessarily mean discarding all provenance. A future implementation may represent one canonical opportunity with multiple source representations.

## 21. Data Not Included in JobOffer

The following remain outside the canonical offer:

```text
matchScore
matchPercentage
matchReasons
recommendation
ranking
explanation
```

These are user-specific or pipeline-specific results:

```text
JobOffer
   +
UserProfile
   ↓
MatchingResult
   ↓
Explanation
   ↓
Recommendation
```

## 22. Generated Summary Rules

The generated `position.summary` must:

1. use only information supported by the source;
2. avoid invented requirements;
3. avoid invented experience levels;
4. avoid invented salary;
5. avoid invented benefits;
6. remain consistent with normalized fields;
7. never replace the original description;
8. remain distinguishable from `sourceSummary`.

## 23. MVP Scope

For the hackathon Proof of Concept, the model is rich enough to demonstrate:

- heterogeneous source ingestion;
- source-specific normalization;
- structured search results;
- complete offer details;
- salary handling;
- remote/location constraints;
- source provenance;
- deduplication;
- matching;
- explainability;
- AI-generated presentation summaries.

It does not require every field to be populated by every connector.

> The canonical model is richer than any individual source; each connector fills only the fields it can reliably support.

## 24. Design Principles

1. **Preserve meaning** — do not merge fields merely because their names are similar.
2. **Preserve provenance** — always know where a canonical value came from.
3. **Never invent missing information** — unknown remains unknown.
4. **Separate source data from generated data** — source facts and AI synthesis remain distinguishable.
5. **Separate offer data from user-specific analysis** — matching and recommendations do not belong in `JobOffer`.
6. **Normalize semantics, not just syntax** — different representations of the same concept map to one canonical meaning.
7. **Keep the model source-independent** — `JobOffer` remains stable when connectors are added or removed.
